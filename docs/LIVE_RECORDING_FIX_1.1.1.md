# Почему запись эфира висела 15 минут без клипов — разбор и исправление (1.1.1)

Дата: 2026-11-21. Затронуты `viralcut/live.py`, `viralcut/db.py`, `viralcut/jobs.py`,
`viralcut/transcribe.py`, `web/app.js`.

## Симптомы

- Идёт «Запись · N мин» (или бесконечное «переподключение»/«подключение»), клипов — 0,
  ошибок в интерфейсе нет.
- Через 15–20 минут записи так и не появляется ни одного ролика.
- Если канал уже не в эфире, приложение молча крутит запросы к yt-dlp.

## Причина №1 (главная): окно не могло извлечь звук

`live._concat_input()` всегда ставил первым файлом `segments/init.mp4`:

```python
parts = [str(init)] + [str(p) for p in paths]
return "concat:" + "|".join(parts)
```

`init.mp4` создаётся только для fMP4-потоков (HLS с `#EXT-X-MAP`). Twitch и Kick отдают
MPEG-TS (HLS v3) — файла нет, и ffmpeg падал с `No such file or directory` ещё до чтения
сегментов.

Дальше срабатывал «тихий» цикл в `process_windows`: ошибка печаталась только в stderr,
`live_processed` не двигался, статус не менялся. Окно повторялось каждые 5 секунд —
бесконечно. Запись при этом шла, поэтому интерфейс показывал «Запись · 15 мин», а клипов
не было и быть не могло.

Воспроизведение на реальной записи Twitch (82 с): 4 попытки извлечения за 20 секунд,
0 клипов, 0 изменений статуса.

## Причина №2: «канал не в эфире» считался сетевой ошибкой

`_hls_url()` пробрасывал `DownloadError("The channel is not currently live")` в общий
обработчик: повтор каждые ~2 секунды без паузы, статус «переподключение» навсегда.
За 15 минут — сотни запросов к yt-dlp и ни одного объяснения пользователю.

## Причина №3: этапы нарезки затирались рекордером

Рекордер каждые 1,5 секунды писал `stage = "Запись · N мин"` и перебивал
«Распознавание речи»/«Рендер клипа». Даже когда обработка шла, пользователь видел только
«Запись · N мин» и «клипов: 0».

## Причина №4: падение обработчика на пустом окне

`ready_count` объявлялся внутри `for` по найденным моментам, но использовался после цикла.
Если окно не дало ни одного момента — `UnboundLocalError`, «Ошибка конвейера», и нарезка
умирала до конца эфира (видно в БД: `cannot access local variable 'ready_count'`).

## Что изменено

| Область | Было | Стало |
|---|---|---|
| Склейка сегментов | всегда `init.mp4` | `init.mp4` только если существует |
| Первое окно | 300 с | 120 с (первый клип ~3 мин) |
| Статусы | «Запись · N мин» затирает всё | этапы распознавания/рендера защищены |
| Офлайн-канал | retry каждые 2 с | `StreamOffline`, статус «Эфир не идёт · жду начала», проверка раз в 30 с, автозапуск |
| Обрыв связи | фиксированные 2 с | пауза 2→4→8→16→30 с, после 3 попыток новый m3u8 |
| HTTP 404/410 плейлиста | «переподключение» | «эфир закончился», ожидание нового эфира |
| Сегменты | по одному | 4 потока параллельно |
| Реклама | пропуск всего 5-минутного окна | пропуск только клипов, пересекающих рекламу |
| Пустое окно | падение | обработка продолжается |
| Очередь эфиров | пул на 3 места, лишние висят на «подключении» | отдельный поток на эфир, лимит 6 с понятной ошибкой |
| UI эфира | только этап | этап, МБ записи, клипы, ошибки, подсказка «эфир ещё не идёт» |

`meta` теперь обновляется атомарно (`db.merge_meta`), поэтому рекордер и нарезчик не
затирают `live_processed`/`live_clips` друг друга.

## Как проверено

- `tools/live_selftest.py` — 8 проверок без сети: склейка MPEG-TS без init, извлечение
  звука, пустое окно, офлайн-статус, «нет связи» (все проходят).
- E2E на реальном Twitch-эфире через API: первый готовый клип на 194-й секунде записи,
  далее окна по 5 минут без отставания, финал `done`, `live_processed == live_duration`.
- E2E из собранного `.app` (frozen, headless): клип появился на 270-й секунде, 5 клипов,
  офлайн-канал даёт «Запись остановлена · эфира не было».
- До исправления тот же сценарий: 20+ минут, 0 клипов, 0 ошибок.

## Если снова «долго»

В `app.log` теперь есть маркеры:

- `[live] extracting 0-120` — начало окна;
- `[live] window 0-120 segments=10`, `[live] found=2` — распознавание и поиск моментов;
- `[whisper] mps/float16 недоступен: …` — если распознавание ушло на CPU (медленнее).

`live_status` в meta: `connecting` / `live` / `offline` / `reconnecting`.

## Дополнение (1.1.2): почему «висит на подключении к эфиру»

**Симптом:** карточка эфира минутами показывает «Подключаюсь к эфиру…», хотя запись
идёт (в БД и в файлах сегменты растут).

**Причина — интерфейс, а не запись.** В `web/app.js` `renderMain()` перерисовывает
карточку только при смене ключа `id:status:число клипов:статусы клипов`. У живого эфира
`status=running`, клипов 0 → ключ не меняется, поэтому вместо полной перерисовки
вызывался только `updateProgress()`. А он начинался с `if (!$("#stageText")) return;` —
в карточке эфира элемента `#stageText` нет (статус был обычным `<span>` без id), поэтому
не обновлялось вообще ничего. Надпись оставалась такой, какой была при открытии страницы:
«Подключаюсь к эфиру…». Обновление происходило только когда появлялся первый клип
(`clips.length` менялся), то есть через 3–5 минут.

**Доказательство:** 16:33:41 в `viralcut.db` — `stage="Запись · 1 мин"`,
`live_duration=82.2`, `live_bytes=67 МБ`, а в окне — «Подключаюсь к эфиру…».

**Исправлено:**

- у полей карточки появились id (`liveStage`, `liveDur`, `liveBytes`, `liveClips`);
- `updateProgress()` теперь сначала вызывает `updateLiveMeta()` и обновляет их каждый
  опрос (1,3 с), ещё до проверки `#stageText`;
- предупреждения «эфир не идёт»/«нет связи»/ошибки обновляются по сигнатуре;
- `loadDetail()` обновляет `stage` и в списке проектов;
- рекордер пишет «Запись · N мин» сразу после разбора плейлиста, до скачивания стартовых
  сегментов (раньше стартовый набор из 15 сегментов скачивался целиком, и только потом
  статус менялся);
- в лог добавлено `[live] playlist ok: N сегментов`.

**Проверка (Playwright, реальный UI):** «Подключаюсь к эфиру…» → «Запись · 2 мин»,
«2 мин записи», «64 МБ» → «Распознавание речи · окно 0:00–2:00» → предупреждение
«Эфир ещё не идёт». Скриншот: `docs/screenshots/live-status-fixed.png`.

## Дополнение (1.1.2): fMP4-эфиры и обрезанные окна

У части каналов Twitch поток отдаётся как fMP4 (`init.mp4` + фрагменты), и внутри записи
встречается скачок таймкодов (например, 30-я секунда → +28 минут). Сегменты склеивались
протоколом `concat:` (байт в байт), и ffmpeg с `-t 120` останавливался на этом скачке.

**Доказательство на реальной записи канала:** окно 0–120 с давало wav длиной
**30.19 с** вместо 120. Распознавалась только первая четверть окна, поэтому
`find_segments` возвращал 0 моментов и клипов не было — при этом статус показывал
«Запись · N мин».

**Исправлено:** окно и клипы собираются через локальный HLS-плейлист
(`#EXT-X-MAP:URI="init.mp4"` + нужные сегменты), который читает штатный HLS-демуксер
ffmpeg. Проверено на той же записи: окно 0–120 → **120.0 с**, клип 35–55 с (уже после
скачка) → 20.0 с. Регрессионный тест `tools/live_selftest.py` теперь собирает fMP4-фикстуру
и проверяет, что окно не обрезается.
