# Changelog

## 1.5.8 — 2026-11-23

**Паузы вырезаются до рендера, реакции аудитории и смены сцен влияют на выбор,
GPU виден на всех видеокартах, а падения на Windows оставляют след в логе.**

- **Частичное скачивание снова работает.** `yt-dlp` для `download_ranges`
  проверяет команду `ffmpeg` в PATH и не смотрит на `ffmpeg_location`, поэтому
  на сборке с бинарником `ffmpeg-macos-aarch64-v9.0` падало «ffmpeg is not
  installed». Теперь в `data/bin` кладутся канонические `ffmpeg` (и `ffprobe`,
  если он есть), ссылка проверяется запуском `-version` и пересоздаётся, а всем
  вызовам `yt-dlp` выставляются и PATH, и `ffmpeg_location`, и contextvar
  постпроцессоров. Если бинарник всё же не запускается — ошибка говорит, что
  именно проверить, вместо «ffmpeg is not installed».
- **«Вырезать паузы» доведено до рендера.** План `analyze.cut_plan` теперь
  исполняется в `render_clip`: видео и звук режутся `trim`/`atrim` и склеиваются
  `concat`, слова пересчитываются `remap_words`, кривая умного кропа — новым
  `reframe.remap_crop_path`, субтитры получают новую шкалу времени. Опция есть
  на главной и в редакторе клипа; громкость измеряется по уже склеенной дорожке.
- **Детекторы реакций и сцен.** Смех (всплеск 1.5–7 кГц с огибающей 4–7 Гц) и
  аплодисменты (широкополосный шум) считаются по звуку на numpy и добавляют
  балл окну; смены сцен — по гистограммам ключевых кадров через OpenCV, границы
  клипов притягиваются к монтажной склейке. Без numpy/OpenCV или без звука
  поиск моментов работает как раньше.
- **GPU в `/api/system` для NVIDIA, Intel и AMD.** PDH-счётчики «GPU Engine»
  читаются с явными прототипами ctypes (без них 64-битный HANDLE обрезался и
  приложение могло упасть прямо во время опроса), 3D-движки суммируются по
  адаптеру и берётся самый занятый; запасные пути — `nvidia-smi` и ADL для AMD.
  В ответе есть `vendor` и `source` (`pdh` / `nvidia-smi` / `adl` / `none`).
- **Windows: диагностика падений.** `faulthandler` пишет дамп в небуферизованный
  app.log вместе с маркерами запуска/остановки, перехватываются исключения
  главного потока и потоков, лог ротируется после 8 МБ, этапы обработки
  пишутся в журнал (`[stage] …`). Добавлен разбор лога:
  `python -m viralcut.diagnostics` (или `tools/analyze_app_log.py`), эндпоинт
  `GET /api/diagnostics` и кнопка «Разобрать журнал» в настройках — отчёт
  показывает, на каком этапе упало, дамп стека и что делать. При этом стек,
  оставленный при закрытии по SIGTERM/SIGINT, не выдаётся за нативное падение:
  «Fatal Python error» пишут только настоящие краши.
- **Самопроверка при старте.** В app.log пишутся `[selfcheck]` строки: путь и
  версия ffmpeg, наличие ffprobe, модель, GPU и источник данных, версия WebView2
  (Windows) и загружается ли оболочка окна. На Windows при фатальной ошибке
  запуска показывается понятное окно (нет WebView2 / pythonnet) вместо тихого
  закрытия, а `/api/health` теперь отдаёт `version`, `platform`, `frozen`,
  `ffmpeg_path` и `ffprobe` — по одному запросу видно, что за сборка запущена.
- **Тестовая сборка под Windows без exe.** `tools/build_portable_windows.sh`
  собирает переносимый ZIP из исходников, `tools/windows_smoke.ps1` проверяет
  приложение без окна (health → `/api/system` ×3 → диагностика → лог), а
  `build_windows.ps1` больше не просит версию вручную и пишет SHA256. Из
  исходников `vendor.tar.gz` теперь распаковывается сам, если папки `vendor` нет.
- **Переносимая Windows-сборка «всё внутри».** `tools/build_windows_embedded.sh`
  (вместе с `tools/resolve_windows_wheels.py`) собирает ZIP ~690 МБ со встроенным
  Python 3.12, всеми зависимостями, ffmpeg и моделью Whisper: пользователь
  распаковывает и запускает `ViralCut.bat`, ничего не докачивая. Резолвер колёс
  сам считает platform-маркеры в окружении win32 — иначе pip с `--platform`
  тянет pyobjc и теряет pythonnet.
- Для тестеров добавлены памятки: `docs/MACOS-TEST.md` (кладётся в DMG как
  «ЧИТАЙ-МЕНЯ.txt») и `docs/WINDOWS-TEST.md` (внутри переносимого пакета).
- Тесты: 108 (было 53): канонический ffmpeg и гейт частичного скачивания,
  trim+concat с субтитрами и кропом, детекторы смеха/аплодисментов и сцен,
  сводка PDH/ADL/`nvidia-smi` и разбор app.log.

## 1.5.1 — 2026-11-22

**Виджет нагрузки, фильтр рекламы и честные HD-фрагменты.**

- **Виджет «Нагрузка»** — плавающая панель в правом нижнем углу, видна на любом
  экране: CPU, RAM (проценты в полоске, объём отдельной строкой — был баг с
  обрезанными гигабайтами), GPU и текущий процесс приложения
  («Рендер: 3 из 8 готово · 65%»). Сворачивается в плашку, состояние помнится.
  Данные — из `/api/system` (macOS: mach-счётчики, vm_stat, ioreg; Windows:
  GetSystemTimes, GlobalMemoryStatusEx, nvidia-smi).
- **Реклама не попадает в клипы.** Спонсорские вставки («этот выпуск
  спонсируется», «промокод», «ссылка в описании», «sponsored», «promo code»)
  распознаются по тексту транскрипта: окна, которые в основном про рекламу, не
  рассматриваются, а клипы, зацепившие рекламу краем, подрезаются.
- **HD-фрагменты в экономном режиме.** Раньше при сбое HD-запроса фрагмент
  молча скачивался в 360p — отсюда «первый клип хороший, остальные мыльные».
  Теперь HD пробуется двумя наборами клиентов (PO-token и android), и только
  потом SD; фактическое разрешение проверяется и попадает в подсказку
  интерфейса с кнопкой «Пересобрать в 1080p».
- **Диагностика**: `VIRALCUT_DEBUG_SECTIONS=1` печатает разрешение каждого
  скачанного фрагмента.

## 1.5.0 — 2026-11-22

**Движок: рендер ушёл на видеокарту, а ресурсы ограничены.**

- **GPU по умолчанию.** Клипы кодируются аппаратным энкодером
  (videotoolbox / nvenc / qsv) с качеством, подобранным замером: `-q:v 75`
  даёт SSIM 0.9905 против 0.9894 у libx264 CRF 19 при том же кадре. Если железо
  не отвечает — автоматический откат на libx264 CRF 19. Отключить:
  `VIRALCUT_HW_ENCODE=0`; проверить в `/api/health` → `hw`.
- **Лимит ресурсов.** ffmpeg больше не забирает все ядра:
  декодер, фильтры и энкодер получают `-threads` (по умолчанию 3 на 8 ядрах),
  число параллельных рендеров — 2, приоритет процесса понижен (`nice 10` на
  macOS/Linux, BELOW_NORMAL на Windows), распознавание речи — на половине ядер.
  Всё в одном месте: `viralcut/resources.py`, настройки через
  `VIRALCUT_RENDER_WORKERS`, `VIRALCUT_FFMPEG_THREADS`, `VIRALCUT_NICE`,
  `VIRALCUT_WHISPER_THREADS`, `VIRALCUT_LOW_PRIORITY`.
- `/api/health` показывает `limits` (ядра, воркеры, потоки, nice) и `hw`.
- Замер: аппаратный рендер 30-секундного клипа — 17 с против 27–38 с на CPU
  (при одинаковом качестве кадра).

## 1.4.4 — 2026-11-22

**Упор на качество: клипы на подвижной камере больше не падают, а приложение не
предлагает 360p по умолчанию.**

- **«Половина рендерится, половина нет» — исправлено.** Причина: путь
  кадрирования на подвижной съёмке требует сотен точек, выражение для `crop`
  переваливало за лимит ffmpeg (~2000 символов) и рендер падал с
  «Error reinitializing filters». Теперь путь сжимается максимум до 60 точек
  (≈1.5 КБ), а если ffmpeg всё равно отверг выражение — клип автоматически
  перерисовывается с упрощённым путём, затем вообще без кадрирования. Клип не
  пропадает ни при каком раскладе.
- **Качество по умолчанию — 1080p.** В окне выбора качества для длинных видео
  рекомендовался 360p («чтобы быстрее»), и пользователи случайно получали мыло.
  Теперь рекомендуется лучшее доступное качество до 1080p; экономия трафика —
  это галочка «Экономно», она больше не снижает разрешение.
- **Кодирование на CPU по умолчанию.** Замер показал, что videotoolbox не
  быстрее (время съедают фильтры), но даёт фиксированный битрейт и хуже держит
  сложные сцены. Теперь libx264 с CRF 19 для 1080p-источников; аппаратный
  энкодер включается `VIRALCUT_HW_ENCODE=1`.
- Сквозная проверка на съёмке с движением камеры: 2 клипа из 2 отрендерены,
  1080×1920, 16 и 14 МБ (до фикса такие клипы падали).

## 1.4.3 — 2026-11-22

**Кадрирование больше не дёргается, а Full HD наконец включается из экономного
режима.**

- **Плавное кадрирование.** Причин было три: сэмплирование всего 2 кадра в
  секунду, быстрый EMA и переключение «говорящего» почти на каждом кадре. Теперь
  замер 3 раза в секунду, медиана по 5 точкам, мягкий EMA с мёртвой зоной
  (0.6% ширины окна), а смена говорящего требует перевеса 2.2× (4×, если люди
  далеко) и удержания 2.5 с. На парном подкасте окно ходит в пределах 65 px
  вместо 1100 px, средний шаг 1.1 px.
- **Путь окна упрощается перед ffmpeg.** Между точками движение линейное, поэтому
  путь уплотняется до 6 кадров/с и сжимается алгоритмом Дугласа–Пекера: форма
  сохраняется с точностью 0.6 px, а выражение для `crop` остаётся коротким.
  Без этого длинные клипы (36 с и больше) вообще не рендерились — ffmpeg падал с
  «Missing ')' or too many args».
- **Full HD из экономного режима.** «Пересобрать в 1080p» теперь поднимает
  `max_height` до 1080 и перерисовывает клипы из фрагментов 1080p *без*
  повторного распознавания речи: 50 секунд вместо четырёх минут. Кнопка видна и
  для экономных проектов, а не только когда сработал откат на SD.
- **Экономный режим на прямых ссылках** (VK, Twitter, свои HTTP-файлы): фрагменты
  и звук режет локальный ffmpeg вместо yt-dlp, который на обычном файле
  зависал или падал. Добавлен сетевой таймаут 30 с, чтобы мёртвый сервер не
  держал рендер вечно.
- Тесты: путь кадрирования проверяется на компактность (≤140 точек, выражение
  < 2000 символов), отсутствие «пинг-понга» между людьми и плотность keyframe;
  отдельный тест рендерит 36-секундный клип с кадрированием.

## 1.4.2 — 2026-11-22

**Исправлен рендер клипов на машинах, где аппаратный энкодер не работает.**

В 1.4.0 появился аппаратный энкодер (videotoolbox / nvenc / qsv), и проверялось
только то, что кодек есть в сборке ffmpeg. На ноутбуках без NVIDIA `nvenc` в
списке есть, но падает при запуске — а откат на libx264 был написан так, что
портил команду ffmpeg. В итоге все клипы падали с невнятной ошибкой
«Filter 'format:default' has output 0 (v) unconnected», и проект уходил в
«Не удалось отрендерить ни одного клипа».

- Аппаратный энкодер теперь проверяется **пробным кадром** (1080×1920, 8 кадров)
  и кэшируется: если железо не отвечает, сразу используется libx264.
- Откат на libx264 больше не «правит» готовую команду, а собирает её заново —
  воспроизведено и закрыто тестом `test_falls_back_when_hardware_encoder_is_broken`.
- В `/api/health` появилось поле `hw` (`h264_videotoolbox` или `null`) — сразу
  видно, какой энкодер реально будет использоваться.
- Если не отрендерился ни один клип, в ошибке проекта теперь причина первого
  отказа, а не общее «не удалось».
- Замер громкости для loudnorm выполняется один раз на клип, а не на каждую
  попытку рендера.
- Тесты рендера (4) добавлены в CI на Windows.

## 1.4.0 — 2026-11-22

Собрано по отзывам на Opus Clip, Vizard и Klap: пользователи жалуются, что
автонарезка «начинается после завязки», «обрывается за фразу до сути», берёт
все клипы из первых минут видео и «смотрит на слушающего, а не на говорящего».

- **Границы клипов по смыслу.** Клип, начинающийся с «Потому что…», «Это…»,
  «So…», теперь захватывает предыдущую фразу (завязку), а клип, обрывающийся
  на «и знаете, что?» или на слове-связке («потому что», «and», «which»),
  дотягивает следующую — вплоть до развязки. Добавлены правила «короткий вопрос
  + короткий ответ» и «фраза оборвалась на запятой или тире».
- **Разнообразие по всему видео.** Лучшие моменты выбираются по временным
  бакетам, поэтому вторая половина длинной записи больше не выпадает из выдачи
  (жалоба «все клипы из первых 10–15 минут»).
- **Меньше дублей.** Перекрывающиеся кандидаты режутся на 18% вместо 30%:
  меньше повторов одного и того же куска в ленте.
- **Активный говорящий в кадре.** Окно кадрирования выбирает того, у кого
  двигаются губы (сравнение патчей области рта между кадрами), с гистерезисом
  на 1.2 с — раньше трекер цеплялся за самое крупное лицо, то есть за слушающего.
  Проверено на парном подкасте: максимальный скачок окна 19 px за 20 с.
- **Заголовки клипов.** Короткие переходы («Что дальше?») больше не становятся
  заголовком: выбирается фраза с хуком, цифрой или конкретикой.
- **Расшифровка оценки в карточке клипа.** Вместо непонятного «⚡ 78» — разбивка
  «хук · подача · эмоции · конкретика · завершённость» и подсказка, что это
  оценка структуры речи, а не прогноз просмотров.
- **Быстрее в 2.3 раза на длинной записи.** Пачечное распознавание
  (faster-whisper BatchedInferencePipeline) и параллельный рендер: 6-минутное
  видео — 231 с вместо 542 с. На том же материале WER упал с 6.5% до 4.7%.
- **Аппаратный энкодер** (videotoolbox / nvenc / qsv) включается автоматически
  с откатом на libx264; отключается `VIRALCUT_HW_ENCODE=0`.
- Тесты: 13 юнит-тестов на границы, контекст, разнообразие и кадрирование,
  плюс сценарные проверки на 6-минутной записи с известным текстом (WER),
  коротком видео, видео без речи, отмене и ретрае.

  (`mweb`+`web`), который перестал отдавать видео и давал «недоступно» на любую

- **Субтитры точнее.** Распознавание переведено с жадного декодирования
  (`beam_size=1`) на beam-search 5 с подсказкой-промптом и запасными
  температурами; звук перед Whisper чистится (срез ниже 70 Гц и выше 7.8 кГц,
  шумоподавление, выравнивание громкости). Сегменты с низкой уверенностью
  перепроверяются повторно с контекстом соседних реплик. На тестовой записи
  ошибок стало меньше (WER 53% → 40% на сложной фразе с брендом и латиницей),
  спорные места помечаются в результате (`quality.weak_segments`).

### По итогам аудита (P0)

- **Локальный API закрыт от чужих страниц.** Убран `CORS allow_origins=["*"]` —
  фронтенд живёт на том же origin, поэтому middleware не нужен, а без него
  сторонняя вкладка не может дёргать `127.0.0.1:порт`.
- **Загрузка файлов проверяется на сервере.** Белый список расширений
  (видео/аудио), лимит размера с обрывом потока (`VIRALCUT_MAX_UPLOAD_GB`,
  по умолчанию 4 ГБ), проверка, что файл действительно медиа — иначе проект
  не создаётся. Шрифты — лимит 24 МБ.
- **XSS/CSS-injection через имя шрифта.** `family` из TTF/OTF теперь проходит
  белый список `[A-Za-z0-9 _-]` до попадания в `@font-face`, ASS-стиль, HTML и
  подпись в интерфейсе; опции шрифтов экранируются через `esc()`.
- **Мёртвый `make_cover` удалён** (падал с `NameError` и нигде не вызывался).
- **Версия из одного источника:** `viralcut/_version.py`; его читают FastAPI,
  PyInstaller-spec (включая `CFBundleVersion`) и `viralcut.__version__`.
- **Правки клипа валидируются до очереди:** `aspect/mode/accent/sub_position/
  sub_speed/sub_font` по белым спискам, числа зажимаются, ошибка — 400 сразу,
  а не «клип упал» в фоне. `body.dict()` → `model_dump()`.
- **Атомарный `meta`:** пайплайн больше не делает read-modify-write и не затирает
  обновления live-рекордера (`db.merge_meta`); heartbeat обновляет только этап и
  не «оживляет» завершённый проект (`db.set_stage_if_active`).
- **Удаление проекта** сначала гасит запись эфира и отменяет обработку, потом
  удаляет файлы.
- **ffmpeg под контролем:** таймаут на первый проход loudnorm, сторожевой таймер
  на рендер клипа (зависший процесс убивается, частичный файл удаляется) и
  живой прогресс через `-progress pipe:1` (в интерфейсе видно проценты).
- **Старт приложения** перенесён в `lifespan` — импорт `viralcut.main` больше не
  создаёт папки и не синхронизирует шрифты.
- **Схема БД:** `PRAGMA user_version` и точка входа миграций; `count_projects()`
  для `/api/health` вместо чтения 200 проектов.
- **Кэш статики:** `Cache-Control: immutable` для `/fonts`, `/userfonts`,
  `/static` — UI не перекачивает шрифты при каждом обновлении.
- **Чистка:** неиспользуемые импорты/переменные в `analyze.py`, typing-импорты в
  `desktop/main.py`.
